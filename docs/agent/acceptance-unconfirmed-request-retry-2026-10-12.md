# 检查点继续反复失败：未确认请求恢复

日期：2026-10-12

## 真实故障

用户点击“从检查点继续”后，确实创建了 `run_b16a844b0c214d3d` 和 `run_72f1adb48dd0449a`，不是按钮没发出调用。两次都在相同工作单元 `99284914408c7d18a06857b0d1dc851a410ae22757fd567d9cada05d17d4e8d5` 返回 `SIDE_EFFECT_UNKNOWN`。

原根任务是 `run_0549592dbf164822`，原步骤 `step_279deb7162d846fa`。与此前 500 章的任务不同，本次批准范围是 89 章，保存了 85 个完整、核验通过的章节分析。两个模型请求停在 `prepared`，业务库 `AgentModelResultCheckpoint` 都没有对应返回；另有一个工作单元在父任务阻止派发后只留下 reservation。

根因是恢复只会尝试查找模型返回，找不到时仍被归类为“可从检查点继续”。重复点击再次创建关联 run、再次查询同一不存在的返回，再次失败。未知请求保护不能直接取消，因为结果缺失不证明请求从未送到模型供应商。

以上通过真实数据库 SQLite `mode=ro` 核对。没有对真实任务调用恢复 API、没有创建新真实 run、没有模型调用，也没有删除或改写用户的未确认请求。

## 修复行为

- 找不到返回时抛出 `MODEL_RESULT_UNAVAILABLE`，保留引用与原请求记录；错误不再混入普通检查点恢复。
- 旧 `SIDE_EFFECT_UNKNOWN` 记录在状态读取时修正恢复描述：`blockedReason=unconfirmed_model_request`，按钮改为“重新请求未确认分片”，明确提示可能重复计费。
- 普通 `failed_node` 恢复被服务端拒绝，不反复创建空转 run。聊天中笼统的“继续”直接返回选择说明，不调用模型、不重新规划、不自动重发。
- 用户点击该明确按钮才发送 `mode=retry_unconfirmed_units`。只允许失败的只读分析阶段，禁止用此模式重放写入阶段或解决未知真实副作用。
- 新关联 run 首先核对同一 owner 的未确认请求。有已保存返回时写回原 journal 并复用；只有明确 `MODEL_RESULT_NOT_FOUND` 才允许重发。网络、存储、格式错误保留原状态并报错，不能视为“请求不存在”。
- 无可找回返回的请求标记为 `abandoned` 并记录授权 run；原 reservation 和尝试预算保留，下一次 `begin()` 生成新请求 ID，追加新预算，不复用旧收费请求 ID。
- 对派发前留下且没有 Runtime request ref 的 orphan reservation 一并释放。其他任务、已完成结果、有原始返回的 reservation 不受影响；仍在执行的原请求不能同时重发。
- 原计划、步骤、锁定 Skill 和已完成结果沿用；收尾 manifest 如存在也保持固定范围。恢复日志展示核对找回数量与获准重试数量。

## 验证

`test_unconfirmed_analysis_retry.py` 复现“部分完成 + 两条 prepared + 一个 orphan reservation”：一条缓存返回被找回，一条缺失分片使用新 ID 重新请求，已完成章节零重复调用；原预算与尝试次数保留，其他 owner 的请求保持 running。覆盖旧状态修正、普通恢复不新建 run、聊天不重规划、终态立即展示明确入口、恢复查询的网络/存储/格式错误不能授权重发，以及写入阶段拒绝该模式。

Python 全量回归 438 passed（285.42 秒，当时包含首批 5 个专项测试）；新增边界与聊天快速路径后，未确认请求、普通重试、重启恢复、已完成结果收尾及意图专项共 90 passed（14.79 秒）。真实 `runtime.chat` 验证“继续”在此状态下零模型调用。Renderer/Electron 类型检查、恢复入口/终态/报告四组 Node 检查通过。

只读冻结本次真实数据确认 **85/89 章** 可用于“仅用已完成结果收尾”，跳过 4 章，manifest `094bdcea85e24140faacd2c720e3cb55ae166030d78c40a68e502cfbb6b53f7e`。真实请求是否已经产生费用无法从本地结果缺失推断，因此界面保留重复计费提示。

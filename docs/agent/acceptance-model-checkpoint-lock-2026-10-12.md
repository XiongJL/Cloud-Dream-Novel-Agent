# 模型检查点写锁与长任务历史写入（2026-10-12）

## 实际故障

只读检查运行 `run_3eb204e3c4a545e3`，它从原任务 `run_4730c9e46b934308` 的检查点继续执行。01:56:33 的错误栈明确指向 `AgentModelResultStore.save` → 结构化响应检查点回调，Prisma 返回 `P2010 / SQLite 5 / database is locked`。

出错请求为第 347 章分析。模型响应已经生成，保存 `AgentModelResultCheckpoint` 失败；该请求没有 Electron 模型检查点，也没有 Python `raw_result_json`。因此不能声称失败章节的返回结果仍可直接复用。第 346、348 章已成功，同一父任务共保留 347 个成功章节分片，路由记录另计。

实际小说业务数据库为 DELETE 日志模式。会话持久化与模型检查点使用同一业务库；会话存储有全局写队列和锁重试，模型响应检查点没有相应保护。会话每次进度保存还逐条重写全部历史事件，随章节数增长形成二次写入量。

日志没有记录 SQLite 锁拥有者，不能认定必定由某个程序或连接持锁，也不能把 347 章当作固定容量上限。可确定的是响应持久化发生了写锁竞争，现有保护不足；内部大量历史重写是已确认的压力来源。

## 修复边界

- `AgentModelResultStore.save` 对同一 Prisma 客户端的检查点写入排队，避免并发版本分配与写入冲突。遇到 SQLite BUSY/LOCKED 时，仅重试已捕获响应的本地读写，最多 5 次，退避 100/250/500/1000 毫秒；不调用生成模型。Prisma 自身的等待仍适用。持续占用明确抛出 `STORAGE_BUSY`，磁盘满等非锁错误直接透传。
- 初始化检查点表的幂等 DDL 同样有有限锁重试。修复没有改变数据库结构、日志模式或依赖版本。
- 会话保存通过一次读取对比已有事件，仅写新增或字段变化的事件；完整历史、事件修订、终态与重载结果仍保留。没有用截断历史来减轻写入压力。
- 分片图在错误跨工作单元边界时保留系统错误分类和详情，避免原始 `P2010` 被转成不可操作的通用失败。
- 只读分析检查点上的锁失败提供“从检查点继续”。旧版失败记录在加载时补齐恢复描述；未知草稿写入与非分析阶段不因此获得重放授权。
- SSE 重连遇到旧失败记录与修正后的终态时，投递最新终态，避免在旧 `P2010` 事件处提前结束、遗漏恢复描述。
- 错误说明使用“数据库读写繁忙”，提示检查原任务恢复入口；不直接假定用户打开了某个占库程序。

恢复原任务会复用成功分片。对于本次第 347 章，旧响应已确认未保存，显式恢复时需重新分析该分片，再继续尚未处理的章节；不会自动重复整本分析。

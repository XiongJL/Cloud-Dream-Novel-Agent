# Agent 系统故障传播审核与修复

日期：2026-10-11。

## 审核结论

这是 Agent 公共基础设施的缺陷，不限于内置文风 Skill，也不属于分批执行提示词的问题。

原链路存在三处断点：

1. 事件先写 SQLite，再通知订阅者。数据库无法写入时，错误事件本身也无法发出。
2. 后台任务的异常处理继续写事件，终态设置依赖这些写操作成功。二次异常会让已退出的任务仍保留 `running`；后台 Task 缺少统一的异常观察。
3. 前端会话自动保存与输入草稿保存只记录 `console.warn`。主进程已经重新抛出错误，前端没有给用户可见提示，也没有通知执行服务停止任务。

实机日志确认发生过 Prisma / SQLite `database or disk is full`。该证据能证明前端保存故障，不能单独证明截图中的旧 Runtime 首次异常堆栈；上述公共断点由代码审核及故障注入分别验证。

## 修复后的约定

- 磁盘满、权限不足、数据库锁定、数据损坏、存储不可用均有独立错误码、用户可见说明及处理建议；这些故障不进入模型自动重试。
- 普通执行异常保留既有工具、工具链、步骤失败事件与恢复信息。诊断事件写入失败也不再阻止终态收口。
- 结束事件与运行快照在同一个 SQLite 事务中提交。写入失败会整体回滚，界面不会收到虚假的完成事件。终态短事务沿用现有同步本地存储边界，避免并发快照覆盖另一个已结束任务。
- 存储故障先让受影响运行在内存中变为 `failed`，停止共用故障状态存储的后台任务，尽力取消已知的上游请求。已有产物、操作标识和结果未知记录保留，不自动重放可能付费或写入的操作。
- 持久化失败时，通过独立的内存事件通知发布 `run_failed`，带 `transient` / `persistenceFailed` 标记。同一 Runtime 内的事件重连可重放此通知；缓存最多保留最近 100 个运行的终态。
- `run_status` 提供 `failure`。故障时可使用内存事件序号，避免状态查询再次依赖故障存储；最后一条持久化事件改为单条查询，避免前端状态核对重复读取全部事件。
- 所有后台执行任务都有退出观察。等待用户确认、等待持久草稿任务下次观察属于正常退出；正常取消和启动前取消保持 `cancelled`。
- 前端保存失败显示持续提示，并向 Runtime 上报识别出的本地存储故障。共享错误格式化先识别存储异常，避免 Prisma 的 `Invalid ... invocation` 被误判为输入错误。
- 会话读取失败也显示持续提示；临时会话不会开启自动保存或草稿刷新，避免覆盖未成功读取的历史记录。
- 前端每 5 秒核对活动运行的权威状态。只有服务明确返回终态时才停止界面工作状态，不因任务耗时长或缺少进度就判失败。迟到的 SSE 事件不会让终态回到执行中。
- 启动执行、状态查询和取消的 IPC 保留结构化错误码及详情。

## 影响范围与限制

采用公共 Runtime、事件总线、状态存储和 AgentWorkspace 的路径都受益；普通任务、内置 Skill、用户 Skill、分批子任务与草稿观察共用这条链路。不修改 Skill 拆分策略、专家审核顺序、模型预算、LangGraph / LangChain 版本或数据库表结构。

共用状态存储失效时停止共享该存储的活动任务，是有意的失败策略。前端不会在尚未通知 Runtime 时单方面宣称执行已经停止；上报失败时仍保留保存失败提示，终态以实际状态查询或事件为准。

磁盘完全不可写时无法保证最后的失败记录跨进程保存。内存兜底仅保证当前进程内通知；重启后沿用既有中断恢复和副作用核对规则。取消上游属于尽力操作，无法据此断言远端请求没有消耗额度或没有提交草稿。

本次没有主动重启用户的应用、清理用户磁盘、重新执行真实模型请求或修改历史任务记录。应用需要加载更新后的 Runtime 与 preload 才能使用完整修复。

## 验证

新增故障注入覆盖双重存储失败、实时订阅与重连、完成事务回滚、后台异常退出、共享故障停止、上游取消、前端上报、禁止自动重试、重启后的终态一致性、正常长任务与启动前取消。

验证结果：Python 全量回归 368 项通过；随后新增的启动前取消边界与故障注入专项共 19 项通过。前端 11 个相关测试脚本通过，包含错误分类、权威终态合并、迟到事件保护、持续提示、结构化 IPC、既有事件重连、运行恢复、重试、取消和审核流程。Renderer / Electron 两套 TypeScript 类型检查通过。仅出现已有的 Starlette / httpx 弃用警告。

## 补充：取消长时间不结束

同样属于公共取消链路的问题。原实现将状态设为 `cancelling` 后依赖后台执行任务完成收尾；后台任务已经退出且没有观察定时器时，取消永远不会结束。上游取消和后台清理还缺少统一的等待上限。前端迟到的取消响应或错误回调可能覆盖已经收到的终态，活动详情中的子操作也可能继续显示转圈。

修复约定：

- 没有后台执行任务的运行也由取消入口收口；重复取消已结束任务保持其终态。
- 并行请求上游取消、停止本地任务和取消持久草稿操作，异步等待最多 5 秒。无法退出的协程不再阻塞取消响应；运行终态阻止继续启动后续步骤。
- 草稿操作即使没有观察定时器也必须请求取消，只有 `cancelled` / `cancel_requested` 才视为确认；正在提交或已完成不能假报取消成功。
- 后台任务未退出或持久草稿取消未确认时，返回 `CANCELLATION_TIMEOUT` / `SIDE_EFFECT_UNKNOWN`，显示失败说明并保留操作标识。禁止据此自动重放任务。
- 本地已停止但上游请求取消未确认时，保留上游未确认标记与检查已有结果的提示；不能保证远端不再消耗额度或提交结果。
- 前端迟到的非终态取消响应和取消错误不再覆盖终态；失败或取消后，仍在等待的子操作显示未完成并停止转圈，已完成的工具结果保留。

只读检查旧任务的磁盘快照已为 `failed`；该证据不代表当时界面的实时 HTTP 状态。此次没有修改旧任务记录或主动重启应用，更新需由 Runtime 与前端加载后生效。

补充验证：新增 10 项取消故障注入，覆盖孤立任务、重复取消、上游阻塞、没有定时器的草稿取消、提交/完成操作拒绝取消、忽略取消的后台任务及迟到执行保护。Python 全量回归 **379 项通过**；5 个相关前端测试脚本通过（系统故障、活动详情、停止按钮、Runtime 契约、运行恢复），Renderer 类型检查通过。

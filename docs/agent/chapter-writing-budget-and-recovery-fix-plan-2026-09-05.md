## 2. 输出额度建议

短期可将本次完整章节验收的最大输出额度设为 **16,384 token**。这是初始建议，不是模型限制，也不是每次生成必须消耗的额度；仅调大额度不能替代后续设计修复。

| 任务 | 初始输出预算建议 |
| --- | ---: |
| 标题、简短摘要 | 512—2,048 |
| 意图识别、计划生成 | 4,096 |
| 单章正文、编辑审校 | 8,192 |
| 启用思考的完整章节生成 | 16,384 |
| 多类素材生成 | 每批 8,192，按类别及条目数拆分 |

以上建议应结合真实用量和截断率调整，不能保证适用于所有章节长度和模型。DeepSeek 文档将思考 token 列为输出 token 的组成部分，因此正文预算需与思考开销一起考虑；字符数不能直接等同于 token 数。[DeepSeek Responses 官方说明](https://api-docs.deepseek.com/guides/responses_api/)

### 目标设计

- 界面默认使用“自动”预算，保留明确的手动覆盖入口。区分期望章节字数、单次生成额度与任务总预算。
- 统一预算计算入口，输入至少包含任务类型、目标字数或条目数、模型能力、思考模式、输入占用和用户限制。
- 部分 Agent 操作已有独立额度限制；本次应整合已有实现，重点修复章节与素材生成直接使用全局 `http.maxTokens` 的路径，避免新增另一套互不一致的计算逻辑。
- 最终额度同时受模型输出上限、剩余上下文空间、用户明确限制和任务总预算约束；预览、上下文组装与真实请求使用同一份预算结果。
- 上下文不足时先减少非必要输入或拆分任务。禁止为了容纳输出而静默丢失用户要求、目标章节身份或审核状态。
- 思考模式通过模型能力适配显式处理，不把同一个 Provider 参数硬套到所有模型。
- 保存输入/输出 token、思考 token（服务提供时）、请求额度、终止原因、耗时和尝试次数。未提供的数据保持未知，不填成 0。
- 保留旧设置的可解释语义；不得在迁移时把用户明确设置的上限静默抬高。默认值迁移策略须在实施时明确。

## 3. 优先修复错误分类与恢复

### 问题入口

- [responsesStream.ts](../../apps/desktop/electron/ai/providers/responsesStream.ts)：`response.incomplete`、`response.failed` 和其他异常当前均可能抛出普通 `Error`。
- [HttpProvider.ts](../../apps/desktop/electron/ai/providers/HttpProvider.ts)：非 `AiActionError` 异常统一落入 `NETWORK_ERROR`。
- [AiService.ts](../../apps/desktop/electron/ai/AiService.ts)：生成、解析、草稿发布阶段之间的错误传播。
- [tool_adapter.py](../../agent_runtime/novel_agent_runtime/tool_adapter.py)、[automation.py](../../agent_runtime/novel_agent_runtime/automation.py)：副作用调用结果与恢复边界。

### 修复要求

- 将输出截断与网络故障分开。建议新增 `MODEL_OUTPUT_TRUNCATED` 或等价稳定错误码，保留 `max_output_tokens` 终止原因、responseId、usage、模型结果引用和已接收文本。
- 部分文本保存为未完成模型结果，不可伪装为成功草稿或自动写回正文。结构化 JSON 截断后必须通过完整解析及 Schema 校验，不能简单拼接后直接提交。
- `SIDE_EFFECT_UNKNOWN` 仅表示无法确认写入结果。只有存在可信的“生成失败且尚未发布草稿”阶段证据时，才可标记为明确失败；不能仅凭异常名称或一次空列表查询推断未发生副作用。
- 确認尚未写入草稿后，允许在既定任务预算内提高额度重试一次。若仍不足，则拆分任务或呈现明确的恢复入口。不得无限翻倍或覆盖用户手动上限。
- 额度调整恢复与网络重试共用任务 deadline、取消信号和调用账本；避免 Provider、Runtime 各自重试而放大请求次数。不得重新执行已成功写入的步骤。
- 界面显示实际原因，例如“生成达到本次输出额度，尚未形成完整草稿”，并区分能直接重试、需拆分、需对账的状态。
- Chat Completions 的 `finish_reason=length` 也应进入等价路径，避免只修 Responses。

恢复设计应与 [运行韧性要求](./retry-failover-resilience-requirements.md) 和 [持久草稿 Operation 要求](./durable-draft-operation-requirements.md) 保持一致，不绕过已有幂等与审核机制。

## 4. 删除占位草稿成功兜底

[AiService.ts](../../apps/desktop/electron/ai/AiService.ts) 的 `generateCreativeAssets` 在 JSON 解析失败后，会构造 `角色-随机编号`、`完成使命` 等占位内容，并按成功返回。本次输出在 Provider 阶段就被截断，**没有走到这个分支**；该风险由代码检查发现。

- 删除将占位数据作为模型成功产物的兜底。
- JSON 解析失败、顶层结构错误、条目不符合 Schema，应记录明确的模型输出错误及可恢复结果引用。
- 不能仅以“能解析为 object”作为成功标准；明确处理数组、缺失必需字段和无有效目标条目的情况。
- 如使用结构修复，必须有次数上限，保留原始结果，修复后重新校验。失败则如实失败，不生成虚构角色、物品或世界规则。

## 5. 修正完整章节任务的计划选择

建议默认链路：

`读取必要资料 → 生成目标章节正文草稿 → 编辑审校该草稿 → 必要修订 → 用户审核 → 写回正文`

- 明确本次交付物是章节正文。用户在要求中提到人物或世界规则，不应自动视为要求创建这些素材。
- 仅当存在影响写作的关键设定缺口时，按需补充相应素材或提出澄清；不要默认启动多个素材板块生成。
- 用户明确要求编辑审校时，计划必须包含可执行的审校步骤。不能只在聊天回复中承诺检查。
- 审校对象必须是本次生成的草稿版本，而非数据库里仍为空的旧章节。修订和审核意见均需关联草稿版本。
- 已完成步骤与成果保留；后续步骤失败时，不能把所有产物视为不存在，也不能整条链路盲目重跑。

排查入口：[IntentService](../../agent_runtime/novel_agent_runtime/intent/service.py)、[意图规则](../../agent_runtime/novel_agent_runtime/intent/rules.py)、[Runtime](../../agent_runtime/novel_agent_runtime/runtime.py) 及 [chapter_continuation.py](../../agent_runtime/novel_agent_runtime/toolchains/chapter_continuation.py)。实施前核实当前计划是模型选择、规则推断还是回退生成。

## 6. 实施顺序

1. **P0：错误分类与证据保留**——正确识别输出截断，保留结果/usage，区分生成失败与写入未知。
2. **P0：移除占位草稿兜底**——错误输出不得被包装为成功产物。
3. **P1：统一任务预算及受限恢复**——采用上述初始预算，补齐模型能力约束、迁移策略和单次额度调整恢复。
4. **P1：计划与审校链路**——避免无关素材生成，确保审校本次草稿并支持必要修订。
5. **真实模型完整回归**——使用同一测试作品完成从请求到审核写回的验收。

短期调大设置仅用于继续验证，不能据此关闭上述缺陷。本轮已完成代码修复和自动化回归，真实模型与审核写回验收仍需单独执行。

## 2. AF-01：失败自动重试与原任务恢复

### 问题定义

模型、搜索或只读工具遇到可恢复网络故障时，不应立即终止任务。自动重试耗尽后，用户输入“继续”“重试”或“再试一次”，应恢复原计划的失败节点，而不是重新生成计划。

### 已确认方案

统一遵循 [Agent 网络重试、熔断、切换与任务恢复设计](./retry-failover-resilience-requirements.md)：

- Agent 图使用 LangGraph `RetryPolicy(max_attempts=4)`，即首次请求后最多重试 3 次。
- `AiService` 每个 LangGraph attempt 只派发一次 Provider 请求，禁止嵌套重试。
- 只重试明确可恢复的网络错误、超时和 HTTP `408/425/429/5xx`。
- 输入、Schema、权限、章节版本冲突和 `SIDE_EFFECT_UNKNOWN` 不自动重试。
- 重试耗尽后，`retry_failed_run` 沿用原计划、范围、审批与检查点创建关联 Run。
- 主模型与后备模型共享最多 4 次网络尝试，切换模型不重置次数。

### 实施任务

1. 把当前大 `advance`、专家执行和模型综合拆成可独立检查点的细粒度 LangGraph 节点或 `@task`。
2. 让可重试异常继续抛给 LangGraph；禁止探索图把所有工具异常吞成普通 observation。
3. 增加稳定错误分类、`RetryPolicy`、节点 timeout、attempt 事件和贯穿各层的取消信号。
4. 移除 `net.fetch` 失败后隐式改用另一 transport 再次派发的路径。
5. 增加 `agent.retry_run` 和 IntentService `retry_failed_run`。
6. 失败卡提供“重试失败步骤”和“调整并重新规划”；Renderer 实现前先完成 Stitch 原型。

### 当前实现（2026-07-22，第四增量）

- 新增 Runtime 统一错误分类，只允许明确的网络错误、Provider 超时、限流和临时不可用进入自动重试；输入、权限、版本、Schema 与 `SIDE_EFFECT_UNKNOWN` 保持单次失败。
- 探索图的模型请求已使用 LangGraph `RetryPolicy(max_attempts=4)`；多项只读工具改为逐项节点/checkpoint，某一工具重试不会重新执行此前已完成的读取。
- LangGraph 提供真实 `attempt=1..4`，Runtime 已保留 `retryAttempt=1..3`/`retryLimit=3` 回调边界；退避使用可取消的异步等待，取消不会继续派发下一次请求。
- 自动重试耗尽后返回规范化错误、attempt、HTTP status（若有）和脱敏 `diagnosticRef`，不会把 Provider HTML 正文传到 Renderer。
- Electron HTTP Provider 一次 attempt 只使用预先选定的 `net.fetch`，已移除失败后改用全局 `fetch` 隐式二次派发的路径；HTTP `408/425/429/5xx` 会形成结构化可重试错误，鉴权和其他 `4xx` 不重试。
- 新增可复用的 LangGraph 单请求节点。计划生成、计划修订、最终报告、Toolchain 模型/专家请求以及执行期只读工具均逐请求应用同一 `max_attempts=4` 策略；宽 `advance` 本身不重试，因此不会重复步骤事件、审批、Artifact 发布或已经完成的业务处理。
- Run 内的每次失败与恢复会持久化 `request_retry_scheduled/started/succeeded/exhausted`，包含真实 `operationId`、`requestId`、step/node/method、attempt、retry limit、退避窗口、错误码、HTTP status 与脱敏诊断引用，可由现有 SSE 重放。计划生成/修订尚无 Run，因此只执行相同策略，不生成伪造 Run 事件。
- 写工具在进入请求节点前按 manifest 分流，继续只经过副作用调用账本；专项测试确认写请求网络结果未知时只派发一次并进入 `SIDE_EFFECT_UNKNOWN`，不会触发请求重试事件。
- 新增 `agent.retry_run`。它只接受带 `expectedFailureRevision` 的失败 Run，只允许恢复真实耗尽的可重试请求；恢复时创建新 Run，保留原 `planId`、审批结果、Artifact、DraftSession/DraftBatch 引用与检查点，记录 `retryOfRunId`、根 Run、恢复次数和失败阶段。原失败 Run 保持不可变，同一失败修订不能并发创建多个恢复 Run。
- `failed_node` 已验证可从最终报告检查点续跑，不会重新执行已完成的 `chapter.get`，也不会重复生成计划或审批；`SIDE_EFFECT_UNKNOWN` 在加载检查点前即拒绝，继续进入人工对账。
- IntentService 已新增窄匹配 `retry_failed_run`：只有当前会话最新 Run 确认为可恢复失败，且消息完整匹配“继续 / 重试 / 再试一次”等短句时才返回恢复参数。该判断在意图模型前本地完成，不会为了发起恢复再调用一次故障 Provider；消息包含新目标、范围或交付物变化时仍进入正常意图与规划链路。Runtime 以自身持久事件核验资格，不信任 Renderer 声明。
- 桌面和 1024px Stitch 原型均已通过。Renderer 已消费真实 scheduled/started/succeeded/exhausted 与 `run_retry_started` 事件，在原活动卡显示“网络波动，正在重试 N/3”、重试恢复和低打扰失败状态；失败卡提供“重试失败步骤 / 调整并重新规划”，诊断编号与 HTTP 状态只在详情中出现。
- 输入“继续 / 重试 / 再试一次”后，Renderer 直接使用 IntentService 返回的恢复参数调用 `agent.retry_run`，不插入新计划或额外助手解释消息；新关联 Run 进入当前会话，原失败 Run 保留在历史中。失败 Run 不再走旧“重新实施”从头执行，`SIDE_EFFECT_UNKNOWN` 也不会出现恢复按钮。恢复事件不改变 Inspector 的折叠状态。
- 当前仍待总 deadline/成本上限、熔断与限流门禁、失败专家专用持久恢复，以及真实 Electron 故障注入人工验收。

### 验收标准

- 前三次网络尝试返回 `504`、第四次成功时，只生成一个最终回答或 Artifact。
- 首次请求和三次重试全部失败时，只显示一条脱敏错误，不显示 HTML 响应正文。
- 自动重试不产生新计划、不重复审批、不重复已完成步骤。
- 用户“继续”后创建关联恢复 Run，并从失败节点开始。
- `SIDE_EFFECT_UNKNOWN` 只进入人工对账，不出现强制重试入口。
- 单个逻辑请求在未配置额外业务流程时最多派发 4 次网络请求。

## 3. AF-02：高频执行失败根因排查

### 问题定义

人工测试中任务执行经常失败，并直接阻断后续验证。当前截图没有展示完整错误码、失败节点、Run ID 和活动明细，因此不能先假设都是网络问题。

### 诊断原则

重试只处理瞬时故障，不能掩盖以下确定性问题：

- Toolchain 输入缺失或 ID 错误。
- Python、Automation、Provider timeout 预算倒置。
- 模型结构化响应或 Schema 校验失败。
- Toolchain 节点异常被错误转换、重复执行或错误归类。
- 章节范围、Artifact、DraftBatch 或 revision 状态冲突。
- Runtime 取消、重启、SSE 断线或调用账本状态异常。

### 实施任务

1. 为失败卡和活动明细补充脱敏 `diagnosticRef`、Run ID、step/node、tool/toolchain、errorCode、retryable、attempt 和 HTTP status。
2. 使用失败 Run 的持久化事件重放完整链路，定位第一个失败事件，而不是最后一个包装错误。
3. 将失败归类为：网络瞬时错误、超时预算、输入/Schema、确定性代码缺陷、版本冲突、副作用未知或用户取消。
4. 对确定性缺陷先编写最小复现测试，再修复根因；不得依赖 AF-01 重试让测试偶然通过。
5. 建立人工测试故障记录模板，至少保存任务目标、角色、章节范围、模型、Run ID、首个失败事件和是否可复现。

### 验收标准

- 任一 `run_failed` 都能在 Inspector 明细中定位到稳定错误码和首个失败节点。
- 相同输入连续执行不再出现同一确定性失败。
- 网络错误进入 AF-01；非网络错误不会消耗三次网络重试。
- 修复后能够继续完成当前团队范围审核和后续人工测试。

### 2026-07-20 修复记录

- 持久化事件确认最近三次失败均发生于 `editor.range_review@1.0.0 / review.synthesize`，上游 `https://api.yintu.cc/v1/responses` 返回 `504 Gateway Time-out`。
- 失败请求均在节点开始后约 61 秒结束；同一节点成功样本在 38 秒完成，符合非流式 Responses 长请求撞上游 Nginx 固定等待阈值的特征。
- 当前 Provider 已验证支持 `text/event-stream`，请求约 2.5 秒即可收到 `response.created`。
- `HttpProvider` 的 Responses 模式已改为 SSE，流式拼接 `response.output_text.delta`，并从 `response.completed` 恢复模型与完整输出。
- HTML 网关错误改为短错误摘要，调试日志不再写入完整提示词和完整长响应。
- 编辑与作者范围报告根据实际章节数收敛输出 Token；单章不再固定申请 6000 Token，20 章仍保留 6000 上限。
- 新增流解析自动化，覆盖 CRLF、分片 delta、completed-only fallback 和失败事件；现有 Agent 恢复测试套件全部通过。
- 已用当前真实 `gpt-5.4` Provider 完整消费 18 个 SSE 事件并成功解析严格 JSON。
- 已通过应用 Automation 重新执行原失败链路：为真实章节《雨夜来电》装配范围上下文并运行编辑范围审核，50.2 秒内成功返回 5 个审核维度和 6 条 finding。

## 4. AF-03：Inspector 内容在阶段切换后不可再次查看

### 问题定义

计划、执行、报告或后续会话阶段切换后，已经生成的产物无法再次点击查看。该问题不只影响产物标签，右侧上下文、审核、证据、工具和角色等内容也可能失去选择状态或数据来源。

### 初步判断

Inspector 当前选择可能绑定了“活动 Run 的临时对象”，而不是稳定的资源引用；Run 终态、下一轮消息或当前步骤变化时，选择状态被清空，历史事件和 Artifact 又没有重新装载。

### 建议方案

- Inspector 选择统一保存为稳定引用：`{ resourceType, resourceId, runId? }`。
- 标签页可见性与 Run 是否执行中解耦；没有当前活动事件时仍可查看历史资源。
- Artifact、Draft、Review、Evidence 和 Tool activity 均从持久化 Store 按 ID 重新读取。
- 时间线中的计划卡、Artifact 链接、报告卡和历史 Run 都可以重新打开对应 Inspector 内容。
- 切换会话、进入下一阶段和 Renderer 刷新后恢复最后一个仍有效的选择；资源已删除时显示明确空状态。

### 验收标准

- 从计划进入执行、从执行进入报告、从报告进入下一轮消息后，旧产物仍可点击。
- Inspector 所有标签可以正常切换，不因 Run 终态被整体禁用。
- 刷新页面和重新打开会话后仍能查看已持久化产物。
- 点击不同 Run 的资源时不会显示上一 Run 的陈旧内容。

## 5. AF-04：任务生成阶段缺少即时思考反馈

### 问题定义

Agent 已回复一段说明后，进入 Intent、计划或任务生成阶段时，界面数秒没有变化，随后一次性出现多条后续内容。用户无法判断请求是否已提交或应用是否卡住。

### 建议状态机

```text
用户发送
  -> 思考中...
  -> 正在理解任务...
  -> 正在整理执行计划...
  -> 已生成计划 / 需要澄清 / 开始执行
```

- 用户消息提交成功后的同一渲染周期内显示 Agent 占位状态，目标小于 100ms。
- 首个 Runtime/SSE 活动事件到达后，原位替换占位状态，不新增重复气泡。
- Planner 调用期间持续显示“正在整理执行计划...”。
- 等待重试时原位显示“网络波动，正在重试 1/3”。
- 失败、取消、需要澄清或计划生成完成时必须结束 loading 状态。

### 验收标准

- 任意发送动作后不会出现超过一个渲染周期的空白等待。
- 慢模型、计划生成和网络重试都能看到连续状态。
- 最终回复、计划卡和活动流不会因占位状态产生重复消息。
- 刷新或 SSE 重连后不会留下永久“思考中”。

2026-07-22 核心阶段增量已完成：

- 复用已确认 Stitch Screen `0882032d3ff84c299f85b7cf3e5e0b68` 的轻量占位样式，不增加新卡片或新布局。
- 临时状态按会话隔离，并在同一位置依次承载“思考中 / 正在理解任务 / 正在整理执行计划 / 正在按意见调整计划”。
- 普通回复、计划完成、澄清、失败与提前校验失败都会清理临时状态；临时状态不写入会话消息，刷新后不会恢复为永久 loading。
- 取消执行不再追加“正在取消当前请求”助手消息，当前 Run 立即切换为 `cancelling` 并由原活动卡展示；取消失败时恢复 `running`。
- 已使用 AF-01 的真实 attempt/limit 事件接入 `网络波动，正在重试 N/3`，失败、恢复和完成会在原活动区域连续更新，不使用定时器伪造重试次数，也不自动展开 Inspector。

## 6. AF-05：综合报告收敛与对话密度

### 问题定义

当前最终报告存在标题重复、Markdown 标记直接显示、正文重复嵌套、内容过长和层次不清等问题；多视角结果、审批内容和过程消息还会进一步放大干扰。目标不只是修好排版，而是让一次审核只产生一份可行动的综合结果，并严格控制对话中的稳定内容数量。

### 建议方案

- Artifact 持久化时区分结构化数据和可读文本，不把最终报告再次嵌入自身内容。
- 标题只展示一次，去掉“计划标题 + 最终报告 - 最终报告”式重复拼接。
- 使用 Markdown 渲染或结构化投影，禁止把 `#`、`##`、`**` 作为普通文本直接展示。
- 默认展示摘要、覆盖范围、严重度统计、关键 finding 和建议动作。
- 长报告按章节或 finding 折叠；需要阅读完整报告时进入现有宽幅审核中心，不扩大常规 Inspector。
- 对 `scope_audit`、专家报告、计划和草稿使用各自 Renderer，不使用一个通用纯文本卡承载全部类型。
- 后端增加重复段落与超长字段校验；模型原始输出保留在受限诊断数据中，不直接进入 UI。
- 多视角审核由 Supervisor 先去重、排序和归并冲突，只向对话发布一张综合报告卡。
- 报告卡首屏只展示最重要的 3 至 5 项；完整 finding、专家子报告和证据按需展开。
- 一次审核到修订只保留报告卡、原位修订进度和最终草稿卡三块稳定内容。

### 验收标准

- 标题、摘要和正文不存在重复块。
- Markdown 标题、列表和强调得到正确渲染。
- Inspector 首屏能看到报告类型、范围、覆盖率、关键结论和主要操作。
- 超长报告不会撑破右栏或形成无法导航的单块正文。
- 同一 Artifact 在 Inspector 与宽幅审核中心展示一致的结构化内容。
- 同一轮多视角审核不会连续出现多份完整报告、重复审批卡或逐 finding 聊天气泡。

### 2026-07-21 补充原则

- 对话中的报告卡先展示摘要、最重要建议和“修改选中项”，不依赖右侧栏完成审核。
- Inspector 可完全折叠且默认不主动展开，只显示上下文、证据和技术明细。
- 完整长报告与长 diff 由用户主动进入专注审核视图；关闭后回到原对话位置。

### 2026-07-21 第一增量实施记录

- 每个 Run 优先选择 `scope_audit`，没有综合审计时选择 finding 最多的专家报告；finding 按严重度稳定排序、去重并默认展示前 4 项。
- 专家子报告不再重复显示为会话产物卡；已有结构化专家报告时抑制重复的纯文本最终报告消息。
- 报告卡支持本次修改勾选、逐项“稍后处理 / 忽略建议”、查看完整依据与一次主操作。
- Inspector 首次默认折叠，按小说在 `localStorage` 记忆状态；报告、草稿与审批事件不自动展开，只有用户显式点击才打开。
- TypeScript、报告投影和完整 `test:agent-recovery` 已通过；实际 Electron 窗口的截图通道超时，桌面布局与交互仍需人工验收，不以 Web 页面替代。

## 7. AF-06：当前对话内轻量处理审核建议

### 产品结论

创作者在任何 AI 工作视角下的主流程都必须留在当前对话。全局任务池继续作为底层持久化和跨会话恢复能力，但产品统一呈现为轻量“待改清单”，不再是审核后的默认去向，也不形成编辑或团队专用后台。

### 建议流程

1. 报告卡按重要性展示建议，用户对每项选择“帮我修改 / 稍后处理 / 忽略建议”。
2. 用户点击“修改选中项”，系统在当前对话创建一个可持久化修订批次；立即处理项默认不进入全局待改清单。
3. 小范围、可逆且只生成草稿的修订，以本次点击作为固定范围草稿生成授权，不再额外要求审批形式化计划。
4. 跨多章结构调整、主线重排、大段删除或范围不明确时，先在对话中显示简洁修订方案，确认后再执行。
5. 时间线原位显示 `第 1/5 项修订 · 正在补强主角动机`；展开后列出本批修订事项及其状态。
6. 同章或相互依赖的建议可合并为一个草稿生成单元，但每项继续保留来源 finding 和独立解决状态。
7. 生成结果统一进入一次草稿/diff 审核；只有用户确认写回或明确手动解决后，任务才进入 `resolved`。
8. 用户可以暂停、跳过或重试失败项；“稍后处理”的建议可从全局入口恢复。

### 2026-07-21 第一增量实施记录

- “帮我修改”保存完整可见决策后，在当前会话生成修订计划并直接启动，跳过普通计划卡审批；正文写回确认与 Runtime 必要安全断点保持不变。
- 计划生成等待期与执行期使用同一类稳定进度组件；折叠态显示 `第 N/M 项修订`，展开态显示创作者可理解的事项与步骤，不展示工具日志。
- 当前 Toolchain 的一次完整替换改写最多支持 5 章；超出范围时明确拒绝启动，不静默裁剪章节。
- 审核存储新增立即修订语义：`createRevisionTasks: false` 时已接受项不进入待改清单；deferred 决策会真实创建或更新 deferred 任务。
- 第一增量遗留的取消、失败和 Runtime 中断回收已在 2026-07-22 第二增量补齐。

### 2026-07-22 第二增量实施记录

- 原“修订任务池”界面已替换为轻量“待改清单”，移除统计看板、固定 360px 详情栏、专家筛选组和“生成可审核计划”。
- 清单只承接“稍后处理”以及取消、失败、连接中断后仍未完成的修订；立即修订仍留在来源对话，不重复进入清单。
- “继续处理”只定位并打开来源对话，同时恢复目标章节范围；不创建新会话、不再次生成形式化计划。
- 用户状态收敛为 `待处理 / 处理中 / 已完成 / 已失效`，搜索、高影响和执行中断筛选按需使用；任务条目使用状态图标，不伪装成待勾选事项。
- 修订 Run 生成草稿后仅进入“处理中”；只有单章草稿或完整多章批次成功写回正文，才自动进入“已完成”。迟到的失败事件不得把已完成或已失效事项重新打开。
- 旧数据库兼容新增来源会话、来源 Run 和进入原因；旧任务可从来源 Artifact 回退恢复会话与 Run。失败、取消和中断同步采用幂等更新，不重复创建清单项。
- 桌面与窄窗口不再使用固定详情列；`1180px` 以下清单占据主内容列，避免页面整体掉入第二个 Grid 行而形成大块顶部空白。
- 已审批 Stitch：`Agent 待改清单 - 桌面主状态 - 七夜（修正版）`（`4a6e0b6d751642ce8347d83388e50ed2`）和 `Agent 待改清单 - 1024px 窄窗口 - 七夜（修正版）`（`b19999bb6d5642ff87d9c8d1bb06fd8a`）。

### 状态建议

```text
pending -> analyzing -> waiting_approval -> drafting -> ready_for_review -> resolved
                     -> skipped
                     -> failed -> retrying
```

### 验收标准

- 当前对话可以选择并启动本轮审核建议，不强制跳转任务池或新建会话。
- 默认流程最多包含“选择要改的建议”和“确认最终草稿”两个作者决策点；高风险修订才增加方案确认。
- 时间线只显示一个原位更新的批次进度，不产生 N 个散乱聊天气泡。
- 折叠态显示 `第 N/M 项修订 + 当前事项`；展开态显示稳定的用户级任务清单，工具、节点和重试不改变 M。
- 已完成任务不会因后续任务失败而重新执行。
- 刷新、取消和 Runtime 重启后可以从持久化批次状态恢复。
- 待改清单与当前会话显示同一任务状态，不形成两份数据。
- 待改清单对所有 AI 工作视角使用同一套 `待处理 / 处理中 / 已完成 / 已失效` 用户状态；复杂内部状态仅在技术明细中可见。
- 任何正文修改仍需草稿审批，不因切换到任一 AI 工作视角而自动写回。
- 任务不能仅因生成计划而标记解决；自动解决必须绑定成功写回和针对性复核，手动解决必须记录原因。

## 9. AF-08：可逆草稿对比与撤销

- 复用现有 DraftSession 的 `baseContent`、`generatedText`、版本和批次来源快照，不另建第二套草稿事实源。
- 默认展示修改摘要与逐处高亮 diff；完整原文与完整草稿作为独立切换视图保留。
- 单章写回补充原文版本/内容哈希校验，与多章批次保持同一冲突边界。
- 写回创建可追溯版本记录，并提供一次操作级撤销；撤销前重新校验当前版本，存在后续编辑时拒绝覆盖。
- 草稿创建只在对话显示结果卡，不自动展开 Inspector。

2026-07-21 第一增量已完成：

- Electron 审核面板已使用轻量 `diff`（jsdiff）生成字符级高亮和增删统计，中文、空文本、全文替换与长未改段落均有投影测试。
- 单章写回和 `chapter.batch_rewrite` 均保存持久化恢复快照；刷新应用后仍可撤销最近一次有效写回。
- 撤销要求正文版本与写回后内容哈希同时匹配；正文被再次编辑时返回 `VERSION_CONFLICT`，不覆盖作者的新内容。
- 撤销恢复正文和小说字数后继续递增章节版本，并重建搜索索引与章节摘要；撤销后的草稿可继续调整并重新写回。
- `sequence_continuation` 的新增章节删除与重排撤销不在本增量内，待新增章节生命周期和顺序恢复能在同一事务内完整验证后再开放。

## 10. AF-09：专注执行模式

- 这是受约束的低打扰模式，不是绕过安全边界的完全控制。
- 自动执行只读上下文获取、AI 工作视角选择、分析和固定范围草稿生成。
- 只在缺少创作偏好、范围不明确或高风险改法冲突时询问，并尽量合并为一次确认。
- 正文写回、版本冲突和 `SIDE_EFFECT_UNKNOWN` 对账永远不能自动越过。

## 11. AF-10：智能工作视角

- 复用 IntentService 的 `suggestedRole`、Operation Registry 和 Capability Matcher，不增加独立分类模型调用。
- 增加 `auto` 视角状态；Renderer 区分系统选择与用户手动覆盖，手动覆盖在当前任务内优先。
- 本轮采用的实际视角以低干扰标签显示；自动选择原因只在按需详情中出现。
- 该项列入后续计划，不阻塞报告收敛、对话密度和可逆草稿审核。

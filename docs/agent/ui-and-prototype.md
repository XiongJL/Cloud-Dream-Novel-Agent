### 2026-07-21 创作者体验方向修订

第一轮 Screen 和现有 Renderer 继续作为已实现基线，但不再代表 Agent 工作区的目标信息架构。软件的唯一用户是小说创作者；作者、编辑、读者、世界观、考据和团队只代表 AI 工作视角。下一轮原型必须遵循：

- 主语言是当前对话。报告摘要、建议选择、发起修订、修订进度和结果确认都能在对话中完成。
- 右侧 Inspector 可完全折叠，首次进入 Agent 工作区默认折叠，并记住工作区选择；新事件不得自动展开或抢占焦点。
- Inspector 只承载上下文、证据、活动明细和历史资源等辅助内容。任何主操作都必须在其折叠时仍可完成。
- 360px Inspector 不再承担完整多章节报告审核；对话卡展示摘要和关键建议，完整证据或长 diff 进入用户主动打开的专注审核视图。
- 全局修订任务池统一降级为轻量“待改清单”，用于稍后处理和跨会话恢复；所有 AI 工作视角共享同一清单，不形成编辑或团队专用后台。
- 审核后的默认操作文案为“帮我修改 / 稍后处理 / 忽略建议”，不要求创作者理解 finding、Artifact、Plan 或 RevisionTask。
- 待改清单默认只展示 `待处理 / 处理中 / 已完成 / 已失效`，高级筛选按需展开，不把内部状态机作为主界面。
- 多视角结果先收敛为一张综合报告卡，默认展示 3 至 5 项，不按专家连续输出完整报告。
- 一次审核到修订默认只保留报告卡、原位修订进度和最终草稿卡三块稳定内容。
- DraftSession 审核从全文左右对照演进为“修改摘要 + 高亮 diff”优先，并补充安全撤销；`draft_created` 不得自动展开 Inspector。

##### 产品原则

- 所有待入库或待应用内容先形成一个 `ReviewPackage`。一个包可以包含多种内容类型，例如角色、情节、设定、物品、伏笔、章节段落和报告建议。
- 审批意见可以挂在包内任意具体锚点上，但“确认入库 / 应用 / 写回”必须按审核包整体提交。不能在同一个包中只提交角色变更而保留情节变更待定。
- 不提供逐条“通过”勾选。Agent 只重写有审批意见的局部锚点；没有审批意见的内容默认认可并保留。
- 取消的是审核包内的“逐项通过 / 准备提交”勾选，不移除报告现有的“帮我修改 / 稍后处理 / 忽略建议”；后者是修订任务处置，不是内容通过确认。
- 存在未发送审批意见时禁止提交当前版本；作者清空意见后恢复提交资格，发送意见后当前版本冻结并等待新版本。
- 重写结果生成一个新的审核包版本，不覆盖旧版本、不自动入库。作者必须再次审核新版本后才能整体提交。
- “只发到会话讨论”和“开始重新生成”必须是两个清晰不同的动作。讨论不会触发生成或修改；重新生成才是执行授权。
- Inspector 的“审核”Tab 是本轮统一审核入口；会话中的产物卡负责进入审核、显示生成状态和回看历史产物。审批意见、重新生成或新版本完成不得自动展开 Inspector。
- 报告类产物复用相同的原位审批意见手感，但最终动作是生成或更新 `RevisionWorkBatch`，不是提交报告本身。

##### 审核包与版本

建议抽象：

```ts
type ReviewPackage = {
  packageId: string;
  sourceRunId: string;
  sourceConversationId: string;
  kind:
    | 'creative_assets'
    | 'chapter_revision'
    | 'chapter_batch'
    | 'expert_report'
    | 'structured_changes';
  version: number;
  basePackageId?: string;
  status: 'pending_review' | 'revision_requested' | 'regenerating' | 'ready' | 'committed' | 'discarded' | 'stale';
  items: ReviewItem[];
  sourceSnapshot: SourceSnapshot[];
};

type ReviewItem = {
  itemId: string;
  type: 'plot' | 'character' | 'worldbuilding' | 'item' | 'foreshadowing' | 'paragraph' | 'diff_hunk' | 'chapter' | 'finding';
  title: string;
  anchor: ReviewAnchor;
  reviewState: 'clean' | 'has_comment' | 'revision_requested' | 'superseded' | 'stale';
};

type ReviewAnchor = {
  targetId?: string;
  targetType?: 'chapter' | 'artifact' | 'draft_session' | 'draft_batch' | 'asset';
  fieldPath?: string;
  paragraphIndex?: number;
  diffHunkId?: string;
  startOffset?: number;
  endOffset?: number;
  quote?: string;
  contentHash?: string;
};
```

`ReviewPackage` 是 UI 与业务语义，不要求第一版立即新增同名表；可以先由现有 `AgentArtifact`、`DraftSession`、`DraftBatchRecord` 和 metadata 投影生成。但 Renderer 和 Runtime 的接口应按审核包思维设计，避免素材审核、文章修改和多章批次各自发明一套状态。

版本回看复用会话历史，不增加独立版本对比页。每次重新生成必须创建新的 Run、Artifact 和 DraftSession，不得通过 `draft.update` 覆盖上一版生成结果；新 Artifact 保存 `revisionOfArtifactId` 和来源审批请求。会话中每张历史产物卡都能重新打开对应审核内容，已被替代、已提交或已丢弃版本只读，并提示是否存在更新版本。

当前实现已经持久化 `conversation.runs`、Run Artifact 引用和旧 DraftSession，但历史入口尚未闭环：时间线会显示旧产物，Inspector 和草稿审核按钮仍只绑定最新 Run。本轮必须增加显式的 `selectedReviewSource`，至少包含 `conversationId/runId/artifactId/draftSessionId/draftBatchId`，使历史卡可以打开其自身版本，而不是隐式读取 `activeRun`。

##### 历史产物归属与访问

历史产物采用“双重绑定”，不能只作为会话内部临时数据：

- `sourceConversationId + sourceRunId` 是不可变来源归属，用于回到原始讨论、定位执行上下文和发起后续重生成。
- `novelId` 是持久化归属，保证切换、归档或删除来源会话后，DraftSession、Artifact、审批意见和写回记录不会被级联删除。
- `targetRefs` 保存产物关联的章节、人物、情节、设定或其他项目对象，为后续从正文和素材侧查询相关产物保留索引。
- `revisionOfArtifactId + reviewRequestId` 组成审核版本链；版本仍在来源会话中按 Run 展示，不把不同会话的产物混入同一时间线。

首版访问边界：

- 会话时间线是历史产物的主要入口，只展示该会话产生的产物。
- Inspector“产物”Tab 展示当前会话全部 Run 的产物，并按版本链归组；Inspector“审核”Tab 打开用户从时间线或产物列表明确选择的版本。
- 切换会话后，Inspector 随当前会话切换产物集合；不会默认显示其他会话产物。
- 删除会话只删除或归档会话入口，不删除其 DraftSession、Artifact、审批意见、写回记录和撤销校验依据。产物显示“来源会话已归档”并保持只读或可恢复审核状态。
- 已提交产物及其写回记录长期保留；真正清理产物必须是独立、明确且经过确认的操作。

本轮不实现小说级全局“产物中心”。后续可以通过 `novelId + targetRefs` 在章节、人物或素材详情提供“相关 Agent 产物”，但这不阻塞当前审批意见、重生成和写回闭环。

##### 本地审批意见

审批意见是审核页内的本地草稿，类似 Codex/GitHub 在某一行或某一块下面添加的未发布评论。

```ts
type ReviewCommentDraft = {
  commentId: string;
  packageId: string;
  packageVersion: number;
  itemId: string;
  anchor: ReviewAnchor;
  body: string;
  status: 'local_draft' | 'saved_local' | 'sent' | 'superseded' | 'cleared';
  createdAt: string;
  updatedAt: string;
};
```

交互规则：

- 每个审核锚点提供“添加审批意见 / 调整这条”入口。
- 展开后显示嵌入式审批意见框，标题为“审批意见”，右侧状态为“本地草稿”或“未发送”。
- 输入框 placeholder 使用“要求 Agent 如何重写这条...”，按钮为“取消”和“保存意见”。
- 保存后在条目下显示浅色意见摘要，支持编辑、清空。
- 底部固定操作条显示“已写 N 条审批意见 · 未发送”，主按钮为“发送给 Agent 重新生成待审核版本”。
- 不显示“准备提交”勾选框。没有意见即默认通过；有审批意见的条目自动进入本次重写范围。
- 只要仍有未发送审批意见，当前版本的整体提交按钮就保持禁用，并说明应先发送或清空意见。

##### 发送与重新生成

点击“发送给 Agent 重新生成待审核版本”后进入确认面板：

- 标题：“发送审批意见给 Agent”。
- 按条目聚合展示所有未发送审批意见。
- 显示执行范围：有审批意见的条目会重写；无审批意见且已认可的内容会保留。
- 主动作：“开始重新生成”，创建新版本审核包。
- 次动作：“只发到会话讨论”，把审批意见带回原会话，不触发生成。
- 取消不会丢失本地审批意见。
- 单章、单篇和素材默认只重写有意见的锚点；多章批次必须额外确认“仅重写本章”或“从本章起重新生成”。

重新生成时会话中只出现一个稳定 Agent 操作卡：

```text
重新生成待审核版本
收到 2 条审批意见，正在生成新版本...

✓ 读取原审核包
✓ 应用审批意见
… 生成新版本
○ 等待审核
```

完成后显示“新版本已准备好”，提供“查看审核”。旧版继续留在原会话产物卡中供只读回看，不提供独立“对比旧版”页面。不自动打开审核页、不自动展开 Inspector、不跳转写作模式或 AI 工作坊。

##### 各审核类型映射

| 审核类型 | 审批意见锚点 | 重写范围 | 最终提交边界 |
| --- | --- | --- | --- |
| 创作素材 | 角色、情节、设定、物品、伏笔等条目或字段 | 有审批意见的条目/字段 | 整个素材审核包整体入库 |
| 结构化报告 | finding、建议项、结论块、证据摘要 | 有审批意见的建议或结论块 | 不提交报告；统一派生或更新修订任务 |
| 单章文章修改 | 段落、选中文本、diff hunk、章节摘要 | 有审批意见的段落或 diff hunk | 整个 DraftSession 写回 |
| 多章节批次 | 章节、章节内段落、章节节拍、批次总评 | 仅本章并复核后续，或从本章起连续重生成 | 连续且非过期的批次前缀提交；同次提交事务整体成功或整体失败 |
| 混合结构化变更 | 不同类型条目共享同一 packageId | 有审批意见的局部类型 | 同一审核包整体入库，不允许跨类型部分提交 |

文章修改必须支持同一能力。区别只在锚点从“素材条目”变为“段落 / diff 块 / 选中文本”：作者可以对某一段写“这里节奏拖了，压缩成两句”，也可以对某个 diff hunk 写“这个改法丢了伏笔，保留原伏笔但换表达”。发送后 Agent 生成新的 `DraftSession` 或同批次新版本，仍需再次审核后写回。

##### 后端与数据契约增量

第一版可以分两层落地：

- Renderer 层先在各审核视图维护 `ReviewCommentDraft`，并在发送时提交给统一 IPC。
- Main/Runtime 层把审批意见转成通用 `review_revision_request`，路由到对应 Toolchain 或现有重生成能力。

建议新增或收敛接口：

```ts
type SubmitReviewCommentsInput = {
  packageId: string;
  packageVersion: number;
  sourceConversationId: string;
  sourceRunId: string;
  sourceArtifactId: string;
  sourceDraftSessionId?: string;
  mode: 'discuss' | 'regenerate';
  comments: ReviewCommentDraft[];
  scope?:
    | { kind: 'commented_items' }
    | { kind: 'all_items' }
    | { kind: 'current_chapters'; childIndexes: number[] }
    | { kind: 'from_current_chapter'; childIndex: number };
};
```

- `mode: 'discuss'`：在原会话插入一条用户可见消息，附带审核意见摘要，不调用生成工具。
- `mode: 'regenerate'`：创建关联 Run，传入原审核包、版本、审批意见和重写范围。
- Runtime 必须校验 `packageVersion` 与来源快照；过期时要求刷新或重新打开最新审核包。
- `mode: 'regenerate'` 必须创建新的 Run、Artifact 和 DraftSession，并通过 `revisionOfArtifactId/reviewRequestId` 形成不可变版本链；禁止原地覆盖旧产物。
- 素材草稿首期需要补齐通用重写能力；当前只有 `creative_assets.generate_draft` 与手动 `draft.update`，不能只靠前端伪装重写。
- 单章和多章可复用 DraftSession / DraftBatch 生成链，但需要把审批意见作为明确约束注入模型输入，并保存到新版本 metadata。
- `current_chapters` 一次接收所有含审批意见的章节索引，为每个目标章生成新版本，保留其他章草稿并统一触发连续性复核；复核通过则保持后续章可审核，发现情节、角色状态、时间线、伏笔、物品状态或钩子冲突时，才将受影响后续章标记为 `stale`。`from_current_chapter` 的 `childIndex` 取所有意见中最早受影响章节，继续沿用当前从指定章起回滚状态台账并重生成全部后续章的机制。

##### 状态与异常

- 本地审批意见未发送：点击“保存意见”后必须按 `packageId + packageVersion` 持久化，切换 Inspector、切换会话或刷新应用后仍可恢复；尚未保存的输入在关闭编辑框或离开审核对象前必须二次确认，不能静默丢失。
- 发送后旧意见标记为 `sent`，新版本产生后旧版本仍可从会话历史产物卡只读打开。
- 生成失败：会话操作卡显示失败，可“重试失败步骤”或“回到审核继续修改审批意见”。
- 来源过期：禁止基于旧包直接重写或提交，提示打开最新产物或重新生成审核包。
- 新版本不满意：作者可以继续在新版本下添加审批意见，再次发送给 Agent；这形成版本链，而不是覆盖同一草稿。
- 整体提交冲突：任一目标版本变化或内容哈希冲突，整包提交零写入，并保留审核意见与草稿。

##### 验收清单

- 同一素材审核包中同时存在角色、情节和设定变更时，不能只提交其中一个类型。
- 审核条目不显示通过/准备提交勾选框；无审批意见时可以直接整体提交。
- 对单条素材添加审批意见后，底部计数、条目摘要和发送确认面板一致。
- 存在未发送审批意见时当前版本不能提交；清空全部意见后恢复提交资格。
- 保存后的本地意见在折叠 Inspector、切换会话和刷新应用后仍能恢复；未保存输入离开前会得到确认。
- “只发到会话讨论”不会创建 DraftSession、不会调用生成工具、不会改变审核包版本。
- “开始重新生成”创建新版本，保留未批注且已认可条目，不自动入库。
- 会话中旧 Run 的产物卡可以打开其对应历史 Artifact/DraftSession；历史版本只读，新版本无需专用对比页。
- Inspector“产物”Tab 能查看当前会话全部 Run 的产物，并按版本链归组；不会混入其他会话产物。
- 删除或归档来源会话不会级联删除 Artifact、DraftSession、审批意见或写回记录。
- 单章 diff 审核支持对段落或 diff hunk 添加审批意见，并生成新的待审核 DraftSession。
- 多章批次可以整体发送分布在多个章节上的全部审批意见。选择“仅重写有意见的章节”时生成这些章节的新版本并统一复核连续性，只在发现冲突时传播 `stale`；选择“从最早意见章节起重新生成”时立即重置该章及其后续章。提交仍遵守连续前缀规则。
- 失败、过期和版本冲突均保留审批意见，用户能回到审核页继续修改后再次发送。
- 桌面与 1024px 窄窗口下，Inspector 审核内容、审批意见框、底部操作条和确认面板无溢出；Inspector 始终保持用户当前折叠状态。

本轮固定交互约束：

- 报告默认只展示 3 至 5 个最高影响问题；专家过程只保留一条轻量完成状态。
- “修改已选”直接创建当前对话修订批次，不再插入一次普通计划审批。
- 修订批次只占一个稳定位置；折叠显示当前项与当前步骤，展开显示作者可理解的业务步骤，不展示工具日志。
- 多章批量改写仍在正文生成前显示章节拍检查点。该检查点嵌在修订批次的稳定位置下，不作为普通计划审批；正文尚未生成时必须直说“正文尚未生成，确认章节拍后开始批量修订”。
- 任一 `waiting_approval` 当前 Run 必须在会话中有且只有一个可提交入口。章节拍确认嵌入唯一的当前批次主卡，不再与独立批次状态卡并列；修订批次 Renderer、活动流和通用确认卡不能重复渲染同一 checkpoint，也不能互相排除后留下无操作状态。
- `DraftBatch` 查看入口从批次创建后持续存在，并依次使用“查看章节拍 / 查看生成进度 / 查看已生成内容 / 打开批次审核”；只有正式草稿产物就绪后才使用“审核”措辞。
- 每个阶段只显示一个主查看动作；不得在卡片头显示“查看节拍”的同时，又在卡片底部显示指向同一批次的“查看章节拍”。
- 最终草稿默认展示“修改摘要 + 高亮差异”；完整原文与完整草稿作为切换视图。
- Inspector 在报告、执行和草稿生成时始终保持用户原有折叠状态，不因新事件自动展开。
- 正文写回仍是最终确认边界；写回后提供带版本校验的撤销，正文已再次修改时拒绝覆盖。
- “待改清单”只包含稍后处理和未完成恢复项；“继续处理”返回来源对话，不新建会话、不生成另一份计划。
- 修订 Run 完成草稿生成时仍显示“处理中”；只有对应草稿或完整批次成功写回正文后才显示“已完成”。

2026-07-21 Renderer 第一增量已按上述原型落地：单章与批量草稿默认进入“高亮差异”，提供“完整原文 / 完整草稿 / 继续调整 / 确认写回”；写回后仅在存在持久化恢复记录时显示“撤销本次写回”。当前安全撤销覆盖单章写回和审核修订主路径 `chapter.batch_rewrite`，不覆盖新增章节型 `sequence_continuation`。

审核后批量修订在对话中只占一个稳定位置。默认折叠态示例：

```text
第 2/5 项修订 · 正在补强主角动机
```

展开后列出本批已选修订项及 `等待 / 处理中 / 待审核 / 已完成 / 已跳过 / 失败` 状态。顶层条目对应作者能理解的修订事项，不对应 LangGraph 节点、Tool 调用、模型请求或重试次数；技术事件继续放在更深一层“活动详情”。

同一章节或相互依赖的多条建议可以共用一个草稿生成单元，但必须保留各自来源和解决状态。已完成项不因后续项失败而重新执行，任务总数在用户确认本批范围后保持稳定。

多章批量改写的稳定位置按以下顺序原地演进：

```text
正在生成章节拍
  -> 待确认 · 2 章节拍（查看 / 调整 / 确认并生成）
  -> 正在生成正文 · 0/2（查看生成进度）
  -> 已生成 1/2（查看已生成内容）
  -> 2 章待审核（打开批次审核）
  -> 已确认写回
```

在 `待确认` 阶段，“查看”的对象是章节拍而不是正文；在生成出首个子草稿前，界面不得暗示已经生成正文。Inspector 在节拍或生成阶段只读并跟随批次状态刷新，不能承担唯一确认入口。

章节拍检查点单卡原型（2026-07-30）：

```text
┌ 章节拍待确认 · 2 章                 [待确认] [查看章节拍]
│ 正文尚未生成。确认章节拍后才会开始生成正文。
│
│ 1. 记忆结晶与第一次觉醒
│ 2. 第二章标题
│
│ [确认并生成                                      →]
│ [告诉我如何调整这些章节拍……                  提交]
│ 已调整 0/10 次
│
└ 节拍记录（默认折叠）
```

确认被持久接受后，仍是同一张卡、同一会话位置：

```text
┌ 正在生成正文 · 0/2                 [生成中] [查看生成进度]
│ 已确认节拍 v1，正文任务正在排队。
│ ○ 第 1 章  排队中
│ ○ 第 2 章  待生成
│
└ 节拍记录（1）
    v1 · 已确认                         查看 v1 节拍
```

视觉与交互约束：

- 确认前不额外显示“章节拍待确认”批次卡；确认后不保留一张同级“确认 N 章节拍 · 已确认”卡。历史节拍只进入当前主卡的折叠记录。
- 当前阶段标题、状态徽标、说明和主动作整体替换，不追加另一张卡；卡片折叠状态、会话滚动锚点和稳定 key 保持不变。
- 裸 `draftBatchId`、`operationId` 和模型调用错误不出现在默认主卡，统一放入“活动详情”。
- 调整产生新 revision 时，当前决策区原位更新为新版本；旧版本进入“节拍记录”，不得在时间线堆叠多张大卡。
- 正文 Operation 为 `queued / leased / running / waiting_operation` 时显示“正在启动”或“正在生成”，只有持久失败、取消或对账阻断才显示“生成未完成”。
- Inspector 快照模式使用 `章节节拍预览 · vR`，实时模式依次使用 `章节生成进度 / 已生成内容 · X/N / 章节生成未完成 / 多章节草稿审核`。外壳与内容区不得重复显示同名主标题。
- 从“节拍记录”打开历史快照不会替换当前批次状态；再次点击主卡的阶段动作时切回实时批次视图。

### `/` 命令与创作技能面板

- 用户在输入框开头或空白边界输入 `/` 时，打开贴近输入框的统一命令面板；URL 和路径中的 `/` 不触发。
- 面板第一组为系统动作：创建创作技能、更新已选技能、管理创作技能、本次不使用技能、新建小说。
- 后续按“内置创作技能 / 我的创作技能 / 当前小说创作技能”分组，数据来自 Runtime 合并 Registry；用户创建的 Skill Pack 以独立类型标识列在所属 Scope 分组中。
- 每项展示类型图标、名称、单行说明、Scope 和版本；Pack 额外显示成员数量；支持关键词搜索、键盘导航、最近使用排序与长列表虚拟滚动。
- 选择 Skill 或 Pack 后，在输入框中显示对应的可移除芯片；Renderer 同时保存 `skill.use` 或 `skill.pack.use` 结构化 Entry Hint，不把 `/skill use ...` 文本交给模型猜测。
- `/skill list` 打开同一列表或管理页，不调用模型；`/skill create` 与自然语言“帮我创建一个 Skill”进入同一 Skill Creator 流程。
- `/novel new` 进入内置新建小说方案，可在后续步骤选择 Skill Pack。

Skill Creator 使用渐进式对话，不强制用户先填写完整表单：

- 从自然语言和已选来源推断用途、正向使用样例、不适用边界与期望产物，仅在关键内容无法可靠推断时追问一个最重要的问题。
- Draft 审核展示“自适应 / 引导式 / 严格”三种指导自由度，并解释它对生成弹性和约束强度的影响。
- 语义选择提供“关闭 / 仅建议 / 自动”三档，用户创建的 Skill 默认“仅建议”；“自动”在正反触发验证通过前保持禁用并展示原因。
- 试运行区区分“结构验证”“正反触发验证”“独立泛化验证”；没有留出样本时不得用绿色状态暗示已验证泛化。
- Run 或 Artifact 的更多菜单提供“改进此创作技能”，打开新的更新 Draft；原 Revision 和历史结果保持不变。

## 折叠式实时活动流需求

实现状态（2026-07-14）：已完成 Run/SSE 事件版。会话中的每个历史或活跃 Run 都显示单条活动摘要，点击后可查看步骤、工具、审批、草稿、终态以及事件 payload 中已有的命令元数据；摘要可由持久化事件 replay 重建。当前 `agent.chat` 只读探索仍是同步调用，只能在回复后显示读取标签，逐条实时活动需在后续统一为可订阅事件。

会话中的 Agent 过程默认呈现为一条安静、持续原位更新的活动摘要，例如：

```text
正在读取当前大纲
正在审计 2 个章节
正在整理人物冲突与节奏问题
正在生成可审核计划
```

默认折叠态：

- 同一个活跃请求只占一个稳定位置，状态变化时替换当前文案，不向会话连续追加“正在……”消息。
- 左侧显示运行状态图标；执行中使用克制的进度动画，等待用户时停止动画并明确显示“需要你确认”。
- 文案来自规范化 `AgentRunEvent` / LangGraph 节点和工具元数据，不直接展示模型的自由文本思考过程。
- 完成后固定为终态摘要，例如“已完成 · 读取 3 项 · 生成 1 份草稿 · 18 秒”；失败或取消显示对应状态和简短原因。
- 折叠态只保留对用户有意义的动作，不显示内部 requestId、checkpoint 序列或重复重试噪声。

点击或键盘展开后显示按时间排序的操作明细：

- 模型阶段：分析请求、选择上下文、整理回答、生成计划或报告；不展示隐藏思维链。
- 工具调用：工具名、用途、脱敏参数、开始时间、耗时、成功/失败状态和结果摘要。
- 命令调用：命令或可执行文件、工作目录、退出码、耗时，以及可折叠的 stdout / stderr；密钥和敏感路径必须脱敏。
- LangGraph 节点：节点名、进入/离开状态、循环次数、checkpoint / resume 结果的用户可读摘要。
- 审批事件：暂停原因、用户选择和恢复时间。
- 产物事件：报告、证据、草稿、diff 或写回结果的引用。

交互与持久化要求：

- 整个活动条均可点击，并提供明确的展开/收起图标；支持 `Enter` / `Space` 和正确的 `aria-expanded`。
- 新事件到达时，展开面板保持用户当前滚动位置；用户在明细底部时才自动跟随最新事件。
- 活动流随会话、Run 和事件持久化；刷新、切换会话、SSE 重连后恢复相同的摘要、展开明细和终态。
- 历史任务默认折叠，当前活跃任务可以记住用户本次会话内的展开状态。
- `prefers-reduced-motion` 下禁用循环位移动画；状态变化通过 `aria-live="polite"` 通知辅助技术。
- 参数、结果和命令输出设置长度上限；完整大对象使用 artifact / 日志引用按需加载，禁止把整章正文复制进活动明细。

## UI 数据流

写作模式快捷桥：

```text
用户点击“质检章节”
  -> 设置 pendingAgentGoal
  -> 切换到 Agent 模式
  -> 打开或创建当前小说下的新会话
  -> 在会话流中插入用户目标
  -> 展示“生成质检计划”建议按钮或计划卡片
```

Agent 会话：

```text
用户输入消息
  -> window.agent.chat
  -> 展示 Agent 回复
  -> 如果是明确任务，自动生成计划草稿卡
  -> 如果是轻量讨论或咨询，停留在普通会话
```

普通会话不能自动创建计划草稿：

```text
用户输入“你好”
  -> window.agent.chat
  -> 停留在会话页
  -> 不调用 window.agent.plan
```

计划草稿入口：

```text
用户提出明确任务，或点击“生成计划草稿”
  -> window.agent.plan
  -> 在当前会话中插入计划草稿卡片
  -> 用户可继续用自然语言要求修改计划
  -> 计划草稿卡展示步骤、工具和“忽略 / 提交 / 实施此计划”
```

明确快捷桥：

```text
用户点击写作模式“质检章节”
  -> 设置 pendingAgentGoal
  -> 切换到 Agent 模式
  -> 创建“第三章节奏质检”会话
  -> 会话角色默认为“团队”
  -> 展示待确认计划卡片
```

执行计划：

```text
用户点击“实施此计划”
  -> window.agent.executePlan
  -> window.agent.subscribeRun
  -> SSE 事件驱动更新当前会话中的执行卡片、工具调用卡片、草稿状态

执行中决策断点：

```text
Python Runtime emit approval_required
  -> 当前 run 状态变为 waiting_approval
  -> 会话流展示“需要你确认”卡片
  -> 用户选择选项或输入补充方向
  -> window.agent.submitApproval
  -> run 回到 running，继续执行
```
```

草稿审核：

```text
Agent 生成草稿
  -> DraftSessionStore
  -> 当前会话插入草稿变更卡片
  -> 用户点击“查看变更”
  -> 对话内展示摘要；按需进入专注审核查看完整 diff / 证据
  -> 用户确认后 draft.commit
```

# 修复旧草稿恢复时的校验顺序

## 原因与修正

真实后续恢复运行 `run_255c300ddf8a4d5a`、`run_7518a7abd95e489b` 在约一秒内重复失败，仍停在 validate。前次改动把旧草稿文件头整理和格式次数升级接到了 compile 分支；损坏文件会先被 validate 拒绝，根本无法执行整理。这是修复接入位置错误。

现将整理放到 validate 中，执行顺序为：读取当前工作区 → 读取并整理成员头部 → CAS 写入实际变更 → 升级格式版本并重置旧格式次数 → 校验 → 内容审核。compile 不再修改已审核的文档，仍检查当前输入哈希与质量记录。

## 新验证覆盖

- 新测试直接调用实际 Runtime 的 validate 分支，使用缺少结束分隔符的旧文件与 styleValidationAttempt=3。验证整理写入先于校验、次数变为 1、进入 quality_review、方法正文及分析引用不变、没有模型/原文请求。再次校验不重复写入，也不再次重置次数。
- 原有恢复测试只验证了重试载入检查点；原有文件测试只证明了独立文件头生成器可以工作，两者没有覆盖实际执行顺序。新的测试补上这一缺口。
- 使用真实失败检查点和三成员草稿的离线副本回放实际 Runtime 分支，通过真实 Native 成员与完整 Pack 校验器。模拟写入使用 Native 的工作区输入失效逻辑重算哈希，遵守 CAS 版本要求。
- 回放结果：三份正文保留，Pack 与所有绑定校验通过，validate → quality_review，validationAttempt=1，模型调用 0，原文读取 0。结果记录：`output/skill-review-10-2026-10-13/validate-replay-result.json`。

本次没有恢复真实收费任务或修改用户数据库。回放只确认旧格式失败能继续进入内容审核，后续真实内容审核及试写仍执行原有质量标准。

# Agent 产品方向

## 核心定位

Agent 化后的 CloudDream Novel Agent 是“写作工具 + AI 编辑部”，不是单一聊天助手。

一级模式只保留两个：

| 模式 | 定位 | 约束 |
| --- | --- | --- |
| 写作模式 | 纯打字写小说 | 正文区域优先，不常驻 Agent 面板 |
| Agent 模式 | 纯交流创作与任务执行 | Codex-like 会话、计划、工具记录、草稿审核 |

编辑 Agent、读者 Agent、作者 Agent、世界观 Agent、考据 RAG Agent 不作为一级模式，而是 Agent 模式内的“创作专家团”角色。

## 写作模式

写作模式保留现有编辑器体验：

- 卷章目录
- 搜索
- 结构/剧情线
- 人物/物品/世界观
- 地图
- AI 工坊
- 灵感
- 正文编辑器

Agent 只作为快捷桥出现：

- 发送当前章给 Agent
- 质检当前章节/选中段落
- 生成下一段
- 请求读者反馈

快捷桥只负责创建 Agent 任务或切换到 Agent 模式，不在写作模式常驻完整 Agent 团队 UI。

## Agent 模式

Agent 模式用于自然语言创作、规划、执行和审核：

- 多会话列表
- 会话流
- 会话内计划卡片
- 会话内执行事件
- 会话内工具调用记录
- 会话内草稿/报告/变更卡片
- 可折叠的右侧上下文与审核 Inspector

Agent 模式的一级体验是“会话”，不是“执行计划页”。执行计划、工具调用、草稿审核、变更审计都是会话流中的结构化卡片。用户在一个会话里提出目标，Agent 在同一个会话里计划、执行、产出报告和草稿。

### 对话优先与专注创作

CloudDream Novel Agent 的唯一产品用户是小说创作者。“作者、编辑、读者、世界观、考据、团队”都是创作者调用 AI 时选择的工作视角，不是不同的人类用户类型。切换视角只改变分析方法、可用能力和输出重点，不改变基础交互语言。

整个 Agent 工作区采用“对话优先、详情按需、创作不中断”的默认体验：

- 能在当前对话完成的审核、建议选择、修订发起、进度反馈和结果确认，不跳转到独立任务管理页面。
- 右侧 Inspector 是辅助信息面板，不承载完成主流程所必需的唯一操作。
- Inspector 支持完全折叠；首次进入 Agent 工作区默认折叠，并记住用户在当前工作区的选择。
- 新消息、报告、Run 或 Artifact 不得自动展开 Inspector。只有用户主动查看证据、上下文、活动详情或历史产物时才打开。
- 窄窗口中的 Inspector 使用临时覆盖抽屉；关闭后返回原对话位置，并在再次打开时恢复上次选择。
- 长报告和长正文 diff 使用按需“专注审核”视图；它是从对话打开并可返回的临时阅读状态，不是新的一级工作模式。

任务、Plan、Artifact、Finding 和 RevisionTask 可以继续作为持久化与恢复对象存在，但创作者不需要理解这些内部名词才能完成创作。

每本小说可以有多次历史会话，例如：

- 大纲设计
- 主角人设重构
- 第三章节奏质检
- 世界观规则整理
- 读者反馈模拟

新建会话时可以选择 AI 工作视角：

| AI 工作视角 | 用途 |
| --- | --- |
| 综合 | 默认，由 Supervisor 协调多个 AI 视角 |
| 作者 | 偏续写、改写、补场景、生成正文草稿 |
| 编辑 | 偏结构、节奏、一致性、伏笔和修改建议 |
| 读者 | 偏阅读体验、困惑点、爽点和追更欲望 |
| 世界观 | 偏设定、角色、物品、地图和术语一致性 |
| 考据 | 偏 RAG 证据、搜索证据和资料整理 |

后续增加默认“智能视角”：IntentService 根据用户目标、Operation 和可用 Toolchain 推荐实际工作视角，创作者只在需要时手动覆盖。智能视角不得增加独立分类模型调用；复用现有 `suggestedRole` 与 Capability Matcher，并在对话中以低干扰方式标明本轮采用的视角。手动覆盖在当前任务范围内优先，系统不能静默改回。

### 会话与任务边界

底部下拉是 Agent 工作模式，不是单纯权限开关：

- `标准`：默认模式。可自动读取、分析并为固定范围生成可逆草稿；低风险任务不重复审批形式化计划，高风险任务先确认简洁方案，写回前始终确认最终差异。
- `只讨论不执行`：纯交流和角色建议，不生成计划草稿，不调用工具。
- `专注执行`：后续模式，类似受约束的 YOLO。自动完成读取、分析、视角选择和草稿生成，合并必要问题并减少中断；不得跳过写回确认、版本冲突和未知副作用对账。

Agent 工作区不是“输入任何话都创建任务”，也不是“所有明确任务都先审批计划”。更准确的流程是：

1. 普通交流：寒暄、咨询和轻量讨论停留在对话。
2. 自动理解：IntentService 识别目标、范围、风险和适合的 AI 工作视角。
3. 低风险执行：自动读取项目上下文、检索证据、生成报告或固定范围的可逆草稿，以折叠进度原位反馈。
4. 高风险方案：跨多章结构调整、主线重排、大段删除或范围不明确时，先展示一版简洁可修改方案。
5. 写回确认：任何正文或结构化数据写回前，都展示最终差异并由创作者确认。
6. 决策断点：缺少创作偏好、范围不清、证据冲突或创作方向分歧时暂停；多个必要问题尽量合并为一次确认。

AI 工作视角不决定是否出现计划。是否展示方案只由任务范围、风险和可逆性决定；只读分析和明确范围的 DraftSession 生成不应重复要求计划审批，写回仍是硬边界。

| 输入类型 | 示例 | 产品行为 |
| --- | --- | --- |
| 寒暄 | `你好`、`在吗` | 只回复问候和能力提示，不生成计划草稿 |
| 咨询 | `你能做什么？`、`这个模式怎么用？` | 只解释能力或建议入口，不生成计划草稿 |
| 轻量讨论 | `这一章是不是太慢？` | 自动读取当前章并给简短判断，不要求计划 |
| 明确低风险任务 | `帮我质检第三章节奏`、`润色这一段` | 自动分析或生成可逆草稿，在对话中反馈进度 |
| 高风险任务 | `重排这一卷主线`、`重写连续五章` | 先确认简洁方案，再生成草稿 |
| 写作模式快捷桥 | `发送当前章给 Agent`、`质检章节`、`下一段` | 绑定当前范围并按风险直接分析、生成草稿或确认方案 |

修订方案出现必须满足至少一个条件：

- 修改跨多个章节且存在顺序或依赖。
- 涉及主线、结构、大段删除或不可轻易撤销的数据变化。
- 范围、创作方向或多个建议之间存在真实冲突。
- 用户主动要求“先给方案”或“先别改”。

当前实现仍以计划草稿作为多数明确任务的门禁；后续按上述风险分级收敛。IntentService、Planner 和 Runtime 继续保存内部计划与检查点，但不要求创作者为每个低风险步骤审批一张计划卡。

IntentService 用于决定目标、工作视角、风险和执行路径，不直接授予写回权限：

```text
用户输入
  -> agent.chat
  -> 识别 Operation、范围、风险和建议视角
  -> 低风险：自动读取/分析或生成可逆草稿
  -> 高风险：显示简洁修订方案
  -> 所有写回：确认最终 diff
```

意图辅助原则：

- 复用 Operation Registry、Capability Matcher、风险评估和 `suggestedRole`，不增加独立分类模型。
- 置信度不足时保持当前视角并按需询问，不能静默扩大范围。
- 标准与专注执行都可以自动完成只读探索和固定范围可逆草稿；专注执行进一步合并非必要中断。
- 写回、版本冲突和未知副作用对账不能由 IntentService 或工作模式绕过。

### AI 结果可靠性与产品化恢复

模型输出 JSON、Schema、Pydantic 对象和跨进程协议都是内部实现，不是创作者需要理解或修复的内容。聊天、计划、报告、Skill 创建、新建小说、专家综合、草稿生成等能力必须共享同一套结果验收与恢复体验；不得把某个结构化输出故障包装成某个 Skill 的特殊问题。

产品层固定以下状态边界：

```text
模型返回
  -> 产品契约校验与安全规范化
  -> 领域规则校验
  -> 产物持久化
  -> 对话发布
```

只有完整通过前述边界并形成可恢复产品对象，任务或步骤才可以显示“已完成”。HTTP 请求成功、模型生成结束或 JSON 可以解析，都不能单独作为产品成功条件。

统一产品要求：

1. **结构化协议是平台能力。** 新增 Agent 方法、Skill、Toolchain 或内置方案时，只声明所需产品对象和边界契约，不自行实现另一套 JSON 提取、校验、修复或错误卡。契约用于 Tool、状态、诊断、持久化和跨进程命令；它不意味着所有长文本创作产物都必须由模型一次性封装成大 JSON。
2. **先验收，后发布。** 未通过完整契约与领域规则校验的模型结果不得进入会话产物、Draft、正式 Skill 或写回流程，也不得短暂显示成功后再回退失败。
3. **自动吸收常见格式偏差。** 语法修复和无信息损失的确定性规范化默认后台完成；仍不合法时执行一次受控结果修复。自动恢复不新增用户消息、不重新规划、不重复读取上下文，也不重复生成已完成产物。
4. **用户处理任务，不处理 JSON。** UI 禁止把 `JSON`、`Schema`、`Pydantic`、字段路径、契约版本和内部错误码作为主要提示或按钮文案。“修复 JSON 后继续”统一改为“修复结果并继续”；活动明细可以说明“结果格式检查未通过”，但技术细节只进入受限诊断。
5. **恢复最小失败阶段。** 自动修复失败后，失败卡在原位置提供“修复结果并继续”；再次失败后提供“重新生成本步骤”或“调整要求后重试”。默认不重跑整个任务、成功专家、上下文读取或已经就绪的产物。
6. **能力之间表现一致。** 同一种失败在聊天、计划、报告、Skill Creator、新建小说和多 Agent 综合中使用相同状态语言、恢复次数和按钮顺序。Skill 不能覆盖平台恢复上限或向用户暴露自己的内部结构。
7. **保留有效进展。** 某个输出校验失败不能抹掉已完成步骤、合法部分结果、用户选择和来源范围。可独立审核的产物继续可见；不完整内容必须明确标注覆盖不足，不能伪装完整成功。
8. **产品发布门禁。** 每个结构化模型方法在进入开发版本前必须完成合法样例、常见类型偏差、缺字段、错误枚举、截断、自动修复、手动恢复和双端契约一致性测试。没有注册完整契约的能力不得出现在 `/` 面板、快捷按钮或自动路由中。

长文本或多文档产物优先采用“受控产物工作区”模式：模型通过受限 Tool 写入应用管理的草稿文档，系统读取真实已提交状态并运行确定性校验，模型根据诊断做最小修改；验证通过后再由产品编译或导入正式领域对象。工作区载体可以是现有数据库对象中的虚拟文档，不要求物理文件或新表。Skill Creator 首先复用 `AgentSkillDraft.draftJson/version/status` 实现该模式，后续可评估扩展到新建小说的小说圣经、人物表、卷纲和章节规划。直接写入只允许发生在 Draft 工作区，不能直接覆盖正式 Skill、小说正文或正式业务表。

用户可见状态统一为：

| 内部阶段 | 默认界面语言 | 用户操作 |
| --- | --- | --- |
| 正在校验或后台修复 | `正在检查生成结果…` / `结果需要调整，正在自动修复…` | 无需操作，可取消任务 |
| 自动修复未完成 | `生成结果未能通过检查` | `修复结果并继续`；次操作 `调整要求` |
| 人工触发修复仍失败 | `这一步的结果仍无法使用` | `重新生成本步骤`；次操作 `调整要求后重试` |
| 保存或发布阶段失败 | `结果已生成，但保存未完成` | `继续保存`，不重新调用创作模型 |
| 项目内容在执行期间变化 | `原内容已发生变化，需要重新确认` | 查看差异后重新执行，不静默覆盖 |

产品验收底线：

- 用户可见的 JSON/Schema/Pydantic/字段路径类错误为零。
- 所有已注册结构化方法都通过同一契约一致性门禁，覆盖率为 100%。
- 结果修复不会创建重复会话消息、重复 Run 目标、重复 Draft 或重复计费调用。
- 模型已返回后的失败可以从最小阶段恢复；应用刷新或重启后恢复入口不丢失。
- 产品按能力和模型统计首次验收通过率、后台修复成功率、最终不可用率与额外等待时间，但不得记录用户原始小说内容。

实现快照与剩余差距（2026-08-22）：

- 已注册的 21 个结构化 Agent 方法均进入 `AgentStructuredOutputContracts` 深层契约门禁；Automation 注册表与契约注册表必须 100% 对齐，新增方法缺少契约时直接拒绝执行。
- 同一契约同时用于生成阶段输出说明、上下文 Token 预算、模型原始结果校验、确定性规范化后的最终结果校验和修复阶段；未通过最终校验的结果不能发布为成功。
- 失败卡主文案和恢复按钮已改为“格式检查未通过 / 修复结果并继续”，Renderer 不再要求创作者处理 JSON；底层技术错误仍只用于诊断与测试。
- Skill Creator 的单 Skill 与文风 Skill Pack 主链均已使用 SQLite 虚拟文档工作区：模型分别写入完整 `SKILL.md`，系统校验已提交文档并只修订出错路径，编译后进入现有审核和原子发布。旧结构化候选方法、Prompt、契约和路由已删除；专用文档树、逐行 Diff 与来源解析仍需补齐。
- SO-2 尚未完成：TypeScript 契约与 Python/Pydantic 仍需收敛到可生成双端类型、校验器和 Fixture 的单一来源，并加入跨运行时 CI 漂移检查、Provider 原生 Structured Outputs 路由和质量指标。
- 全模型调用的 `model_received` checkpoint、保存/发布阶段独立恢复与跨版本重处理仍需按恢复需求继续补齐，不能因本轮契约门禁完成而视为整条可靠性链路完成。

技术恢复协议、契约治理和分期实施见 [Agent 运行韧性、重试、降级与任务恢复需求](./retry-failover-resilience-requirements.md)。

推荐交互：

```text
用户：你好
Agent：你好。我可以帮你做章节质检、续写、结构梳理和草稿生成。你可以直接描述目标，或从写作模式发送当前章。

用户：帮我看看第三章追更欲望够不够
  -> 自动采用读者视角读取当前章
  -> 对话原位显示分析进度
Agent：给出一张综合审核卡，首屏展示最重要建议

用户：把选中的三项改一下
  -> 当前对话显示“第 1/3 项修订”
  -> 生成可逆草稿，不自动写回

用户查看高亮 diff 并点击“确认写回”
  -> 校验章节版本
  -> 写回并记录可撤销版本
```

## 会话内产物与审核

Agent 产物以内嵌卡片进入会话流，右侧 Inspector 只用于按需展开细节。所有 AI 工作视角的主操作必须保留在会话卡片内，不能因为 Inspector 折叠而不可用。

| 会话卡片 | 右侧 Inspector |
| --- | --- |
| 计划卡片 | 步骤详情、工具列表、审批状态 |
| 执行卡片 | Run 状态、事件时间线、失败原因 |
| 工具调用卡片 | 输入参数、输出摘要、RAG 证据 |
| 质检报告卡片 | 分项评分、问题列表、证据引用 |
| 草稿变更卡片 | 正文 diff、结构化 diff、接受/拒绝 |
| 审核结果卡片 | 写回状态、版本、回滚线索 |

审核变更不作为独立一级模式。单次会话内先在报告卡查看摘要、选择建议并发起修订；需要核对完整证据或长 diff 时，再主动打开 Inspector 或专注审核视图。全局“待改清单”只作为跨会话积累和恢复入口。

审核后的默认链路为：

```text
审核报告卡
  -> 选择“帮我修改 / 稍后处理 / 忽略建议”
  -> 点击“修改选中项”
  -> 当前对话原位显示修订进度
  -> 展示草稿摘要与差异
  -> 用户确认后写回
```

小范围、可逆且只生成草稿的修订，不再要求用户额外审批一张形式化计划；“修改选中项”本身构成对固定范围草稿生成的明确授权。跨多章结构调整、主线重排、大段删除或范围不明确时，仍必须先显示简洁的修订方案供用户确认。无论是否显示方案，写回正文前始终需要最终草稿或 diff 审核。

创作者看到的每条审核建议必须优先回答“哪里有问题、为什么影响阅读、建议往哪个方向改、依据是什么”。严重度、专家来源和技术标识是辅助信息；`全部接受`、Artifact ID、Finding ID 和内部状态机不得成为默认阅读负担。

多视角审核默认只向对话发布一份综合结果。Supervisor 先完成去重、排序和冲突归并；对话首屏只展示最重要的 3 至 5 项以及“查看全部”，专家子报告与分歧证据按需展开。不得把每位专家的完整报告、审批表和重复 finding 连续投影到会话。

一次审核到修订的默认对话密度固定为三块稳定内容：一张审核结果卡、一条原位更新的修订进度和一张最终草稿卡。内部工具、专家阶段、审批记录和重试不得额外形成聊天消息。

跨会话积累的建议统一进入轻量“待改清单”，而不是按 AI 视角拆成不同任务系统。创作者默认只看到 `待处理 / 处理中 / 已完成 / 已失效`；内部 `open / planned / deferred / resolved / closed / stale` 状态继续服务恢复和审计，但不直接成为主要界面语言。清单支持按章节、人物、情节线和来源视角归类，从任一条目继续时仍回到对话处理。

待改清单只接收“稍后处理”、执行中暂停或尚未完成的事项。当前对话立即完成的建议不先进入清单；完成项自动归档，避免清单退化成长期任务管理系统。

## 写回边界

所有正文和结构化数据变化必须进入草稿审核：

```text
Agent 生成结果
  -> DraftSession
  -> 会话内草稿/变更卡片
  -> 对话内摘要与按需专注审核
  -> 用户确认
  -> 写回正文/结构化数据
```

未经用户确认，正文不变化。

现有 DraftSession 原文/草稿左右对照继续保留，但需要演进为可逆修改体验：

- 默认先展示修改摘要和逐处高亮 diff，再按需切换完整原文/草稿。
- 单章与多章草稿使用一致的差异语言，明确新增、删除、替换和受影响章节。
- 写回前固定原文版本与内容哈希，冲突时零写入。
- 写回后提供明确的版本记录和一次操作级撤销；撤销同样校验当前版本，不能覆盖用户后续编辑。
- “确认写回”后才允许自动完成对应待改事项。
